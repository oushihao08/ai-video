# 播讲稿写作

写给听者理解与声音表演的正文。可从本期骨架起稿，也可改现成稿；只写稿时不强制进入分镜。

## 输入

读取当前目标、表达与事实边界、`outline.md`（若有）、相关 `research/` 原文和待改稿。外部稿无研究过程时保留原稿副本，不补造来源或骨架；有事实缺口则定向回查或明确限制。先核对 [内容原则](../story-plan/references/content-principles.md) 与 [交接约定](../../references/handoff.md)。

## 写稿

1. 把骨架每段的必要信息写成实际可听懂的叙述，不只复述段落职责。检查关键行动的条件、关系、选择依据和后果；机制解释检查前提、过程和限制。事实、推断和虚构保持各自身份。
2. 用 `<episode>/script.md` 作唯一口播正文。格式为 `## [seg-01] 标题`、`[s001] 口播句。`；必要表达另写 `> 表达 [s001]：具体作用。`。不把来源、计时、舞台说明塞进口播句。既有句改措辞时保留 ID；拆合句时分配新 ID 并告知下游更新引用。可用共享 `parseScriptMarkdown()` 检查格式；它不判断内容质量。
3. 表达标注只放在平读会损失关键含义的地方，说明重音、态度或停顿的作用。不要按句平均分配情绪。估时来自骨架/编辑判断；真实秒数由 story-voice 后续测得。
4. 完整视频在正式配音前，和 story-video 用同一句段 ID 核对新信息由谁交代、何处需要停顿或读图、画面是否暗示额外事实。视频方改镜头，写稿方只修正文；实质修稿后重新审核。画面承担的必要内容须有可检查的设计，不能替尚未实现的效果做保证。
5. 作者直接读最终正文并修正已发现问题：事实与原文是否一致、主脉络是否兑现、关键解释是否出现、指代与术语是否适合听、重复说明是否有作用、标注是否过度。将自审发现和改动记录在 `<episode>/episode.md`，不要自行写出独立审核通过结论。

交付正文、句段 ID、必要表达标注、来源关联和未解决项。新写或实质改写的 AI 正文须交 story-review 独立审核；单独写稿可停在这里，明确审核状态。仅改表达标注且正文语义不变时，正文审核依据可沿用，但声音输入需要更新。
