# 播讲稿写作

对实际作品负责：让语言与必要声画表达完成当前任务。骨架是构思依据，不能替正文已经说出来的内容。

## 输入

先读当前用户要求与 `requirements.md`，再读实际材料、骨架或待改稿。读取 [内容判断与方法选择](../story-plan/references/content-principles.md)、适用专项与 [交接](../../references/handoff.md)。区分原始要求、作者选择、事实与例子；外部稿保留原文，冻结或局部修改按明确范围处理，不补造研究过程。

## 写作

1. 依据本期目的选择实际叙述与语言，让具体材料承载理解和感受。按适用方法组织，从材料可直接写稿，简单任务不强制先造详细骨架。核验缺口定向回查，不用漂亮连接补事实。
2. 检验骨架：段落无作用、重复、连接薄弱或目标偏移时，删并重排并同步 `outline.md`；核心目标改变返回策划决定。不要为忠实填充骨架而保留缺陷，也不擅自重写未授权范围。
3. 用 `script.md` 作唯一正文：`## [seg-01] 标题`、`[s001] 口播句。`，必要时另写 `> 表达 [s001]：具体作用。`。研究说明、来源清单、秒数和舞台动作不塞进朗读句；省略会误导的归属与限定在正文需要处表达。改措辞保留 ID，拆合句分配新 ID 并更新下游引用。
4. 按听者实际接收顺序处理主体、术语和必要连接。重复、长短句、问句和留白按作用使用，不按配额。问句若只拖延已能说明的内容就修正；空泛升华、狠话或“深度”过渡若没有实际作用就删，不能换同义修辞维持空段。
5. 声音标注只在平读会损失含义或效果处写具体重音、态度、停顿及作用。估时是编辑判断，实测由声音阶段提供。完整视频正式配音前和 story-video 对齐关键表达由谁承担、如何读懂、何处需要留白；尚未实现的画面不能替正文承诺作保证。

## 自审与交付

直接读最终正文，对照原始要求检查实际表达对象、材料支持、理解缺口和无作用部分；不要只对照自己写的骨架。将具体发现与修订记在 `episode.md`，用户要求和自主选择仍各保持身份。

交付正文、句段 ID、必要标注、来源关联和未解决项。新写或实质改写 AI 正文交 story-review 独立审核，作者不写独立通过结论；只要稿件就在此停止。仅标注变更且语义未变可沿用正文审核，声音输入需更新。格式解析只能核对结构，不能评价内容好坏。
